# Performance Report — 17 Nov 2026

Everything below was **measured**, not estimated. Where something could not be
measured here, that is said plainly (section 6).

**Where the numbers come from (developer workspace, not your PC):** Linux, 2 CPU
cores, 7 GB RAM, Dart **3.11.4** (the SDK of Flutter 3.41.6), the app's real
services on a real **Hive** database opened exactly as `main()` opens it,
compiled ahead-of-time like a release build. Each timing is the median of 5 runs
(1 run for slow one-off actions). Old laptops will be slower in absolute terms;
the before/after ratios are what matter. You can repeat every measurement on
your own Windows or Mac machine with `tool/perf` (section 7).

**Test data** (generated by `tool/perf/seed.dart`, same record shapes the app
writes, never your real data):

## 1. Audit — the bottlenecks that were actually found

Measured on the large dataset with the code as it was before this work.

| # | Bottleneck (measured) | Cause in the code |
|---|---|---|
| 1 | **Every read decoded a whole box**: e.g. listing invoices 711 ms, products 125 ms, every report ≥ 74 ms even with 0 rows. | `HiveStore.values()` deep-copies every record and every service then ran `Model.fromJson` on all of them, on every call. Nothing was cached. |
| 2 | **Dashboard took 7.7 s to build — and again after every change** (each sale, payment, even an error-log write). The 6-month chart alone was 3.9 s. | `DashboardPage.build` calls ~20 service queries; together they decoded the 50,000 sales about 13 times. `liveServicesProvider` rebuilds it after any commit. |
| 3 | **Top bar: 260 ms every 20 s and after every change.** | Its notification bell scanned all products and all 10,000 serials (and read each serial's product separately) on every rebuild. |
| 4 | **Reports: all 29 took 30.7 s; the sales report 941 ms.** | Each report decoded all sales, products, customers, suppliers and technicians up front, even reports that use none of them; the daily-sales report created a new date formatter for each of 24,000 invoices. |
| 5 | **PDF of a 2,000-row report: 13 s, window frozen the whole time.** | One table spanning ~50 pages with automatic column widths: the pdf package lays the whole remaining table out again for each page (time grows with rows × pages). It also ran on the UI thread. |
| 6 | **Backup Now froze the window for 4.6 s** (total 12 s). The startup auto-backup did the same. | JSON-encoding all 334,000 records, SHA-256, zip compression and the read-back check ran on the UI thread; with an external folder the data was encoded twice. |
| 7 | **Excel/CSV export froze for 0.5–0.9 s.** | Encoding on the UI thread. |
| 8 | **Search 132 ms per keystroke, unknown-code scan 118 ms.** | Search decoded and re-sorted all products on each keystroke; a scan that was not a barcode/serial fell back to decoding every product to compare SKUs. |
| 9 | **Selling: FIFO costing re-read all cost layers for each bill line.** | `openLayers` filtered the whole cost-layer box (20,000 layers) per line. |
| 10 | **Startup: nothing on screen for ~3 s.** | `main()` opened every Hive box (122 MB) before the first frame. |
| 11 | Long lists built every row widget up front (label-printing dialog with all products, POS serial picker, product serial history). | `ListView(children: [for …])`. |

What was checked and found **not** to be a problem: barcode/serial scan via the
index (<0.1 ms), adding a product to the bill (<0.1 ms — model math only),
customer list (10 ms), saving a sale (121 ms, mostly the disk flush that keeps
data safe — left as is).

## 2. What was changed

No database schema change, no data migration, no change to any business
calculation, no feature removed. Data files are opened and written exactly as
before.

1. **Read cache** (`ServiceContext.all` / `derived`, `context.dart`). Decoded
   records are kept per box and reused until that box changes. Each store now
   has a per-box **revision counter** (`DataStore.revision`) that is increased
   synchronously before and after every write of a commit, so a cached list is
   never used after its data changed — not even for a read made during a commit.
   Cached lists are unmodifiable and models are immutable, so a screen cannot
   change cached data. All services read through the cache. The stock-movement
   log (largest box, rarely read) is deliberately **not** cached, to save memory.
2. **Indexes built from the cache**: products sorted by name with lower-cased
   search text; SKU → product (scanner fallback); cost layers by product (FIFO);
   ledger lines by party (statements); products by id (warranty list).
3. **Reports**: lookup tables are built only by the reports that use them;
   date formatters are created once per report.
4. **PDF reports**: rows are laid out in blocks of 20 with fixed column widths
   proportional to the longest text of each column (what the automatic widths
   were based on); the header row still repeats on every page. Same content,
   same columns, same totals. Built on a background isolate.
5. **Excel / CSV export**: encoded on a background isolate.
6. **Backup**: a consistent snapshot of all records is taken in one step
   (commits made afterwards are not included — as before); the JSON text is then
   produced in small slices so the window keeps drawing, and SHA-256 + zip +
   the read-back verification run on background isolates. `data.json` is
   byte-for-byte identical to the old encoding (tested). Manual and automatic
   backups now encode once and write the same bytes to both folders. Reading and
   checking a backup file (restore, backup history) also runs off the UI thread,
   with the same checks.
7. **Startup**: the window shows the splash immediately (in the saved light /
   dark theme), while the database opens behind it; the splash then pre-loads the
   Dashboard's data, so the Dashboard's first frame is fast. The splash still
   shows for at least 1.4 s in total, now counted from launch (no longer added on
   top of the database opening time).
8. **Rebuilds**: writes that only add to the internal error log no longer
   rebuild every screen.
9. **Long lists**: the three lists in issue 11 use `ListView.builder`.

Files: `lib/data/store/{data_store,hive_store,memory_store}.dart`,
`lib/domain/services/{context,app_services,catalog_service,inventory_engine,party_service,report_service,report_tables,backup_service,warranty_repair_service}.dart`
(plus the mechanical cache switch in the other services), `lib/printing/pdf_docs.dart`,
`lib/ui/print_actions.dart`, `lib/ui/providers.dart`, `lib/ui/splash/splash_screen.dart`,
`lib/main.dart`, `lib/ui/pages/{reports,products,pos}_page.dart`.
New: `test/performance_cache_test.dart`, `tool/perf/seed.dart`, `tool/perf/bench.dart`.

## 5. Memory (process RSS)

| Point | 1k/5k — before | after | 10k/50k — before | after |
|---|---|---|---|---|
| After opening the database | 107 MB | 107 MB | 660 MB | 660 MB |
| After Dashboard | 116 MB | 123 MB | 770 MB | 735 MB |
| After visiting the main pages | 122 MB | 128 MB | 683 MB | 787 MB |
| After all reports + PDF/Excel/CSV | 222 MB | 344 MB | 1539 MB | 1585 MB |

Honest reading: the cache keeps decoded records in memory, so after visiting
the main pages the large shop uses about 100 MB more (787 vs 683 MB); peaks after
reports and exports are about the same as before. Most of the memory is Hive
itself, which keeps every record in RAM (660 MB for the 122 MB large database,
107 MB for the medium one) — that is unchanged and would need a storage change
to reduce, which was not done because the task forbids schema/storage risk.
Dart frees memory lazily, so RSS readings taken right after a background
isolate finished (backup) are high-water marks, not leaks. Every new `Timer`,
`AnimationController` and text controller in the changed files is disposed.

## 6. What was NOT measured here (needs your machine)

* Flutter frame times, widget rebuild counts and GPU/raster time — the Flutter
  engine cannot be downloaded in the developer workspace (`storage.googleapis.com`
  is blocked), so screens were not rendered. The numbers above are the Dart work
  each screen does in `build()`, which was the dominant cost.
* Real Windows hardware (older laptops, HDD vs SSD).
* Printing to a real printer.

Use Flutter DevTools (Performance + Memory tabs) on Windows with the large test
database to confirm.

## 7. Reproduce on your computer

```
dart run tool/perf/seed.dart  perf_db_large 10000 50000 10000
dart run tool/perf/bench.dart perf_db_large large
```
`seed.dart` only writes into a new/empty folder (it refuses any other folder, so
it can never overwrite real shop data). `bench.dart` copies the database to a
temporary folder first and never writes to the source. `tool/run_tests_mac.command`
now also runs it (log: `verify_logs/ui_06_perf.txt`).
